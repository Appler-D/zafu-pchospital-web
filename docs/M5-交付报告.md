### 新增索引及理由

无。四类正式查询在目标 GreatSQL 上均已命中既有索引，未出现 `repair_records` 的全表扫描，
按任务书「只有证明确有必要时才新增」的要求，不添加重叠索引。

### EXPLAIN 摘要

测试数据量：总记录 **3605** 条（其中本次注入 3600 条）、ACTIVE 成员 **116** 名；
注入方式为 60 名成员 × 12 个月 × 5 条，跑完即清理。

| 查询 | 关键计划片段 | 结论 |
|---|---|---|
| ① 个人统计 | `Index lookup on rr using repair_records_member_status_date_idx (member_profile_id=…, status='APPROVED')` | 命中现有复合索引 |
| ② 分类分布 | 同上索引 + `Aggregate using temporary table` | 组内行数仅该成员自身记录，临时表代价可接受 |
| ③ 月度趋势 | `Index range scan on rr using repair_records_member_status_date_idx over (… AND '2025-10-01' <= repair_date < '2026-10-01')` | 日期窗口下推为索引范围扫描 |
| ④ 分组排行 | `Index lookup on rr using repair_records_status_submitted_idx (status='APPROVED')` + `Single-row index lookup on mp using PRIMARY` + `Window aggregate: rank()` | 维修表按正式状态走索引，成员档案走主键回表并过滤 ACTIVE/未删除；聚合/窗口的临时表与排序是 `GROUP BY` + `RANK()` 的固有代价 |

`repair_records` 上唯一的既有索引 `repair_records_member_status_date_idx`
（`member_profile_id, status, repair_date`）正好覆盖成员维度 + 状态 + 日期窗口，
因此没有新增索引的证据。

无 DDL，不涉及锁表；无回退需求。

## 统计口径核对

- **APPROVED + deletedAt IS NULL**：唯一谓词来源仍为 M2 的 `approvedRepairWhere()`。
  原生 SQL（窗口函数与 `DATE_FORMAT` 无法用 Prisma 查询构造器表达）里的谓词由
  `approvedRepairSql()` **从同一入口机械翻译**，并对「状态是字面量、删除条件是 `IS NULL`」
  做运行时断言 —— 一旦有人改动 `approvedRepairWhere()`，这里会立刻抛错而不是静默沿用旧口径。
- **日期**：复用 M3 的 `resolveMemberRanges()`（内部即 `shanghaiMonthRange` 与学期配置），
  三个入口（工作台 / 个人主页 / 排行榜）共用同一套 `Asia/Shanghai` 规则。
  实测确认 `repair_date` 是 `DATE` 列，M3 的 UTC 半开区间在它上面的比较语义
  **恰好等价于上海自然月首末两天**（`8/31 → 排除`、`9/1 → 包含`、`9/30 → 包含`、`10/1 → 排除`），
  因此月度分桶直接用 `DATE_FORMAT(repair_date, '%Y-%m')`，**不加时区偏移**。
- **数量 / 时长**：数量取有效记录数；时长取 `SUM(duration_minutes)`，单位恒为分钟，
  `NULL` 按时长 0 计入且不让榜单失败；小时只在 UI 层用既有 `formatDurationMinutes` 格式化，
  排序值不受影响，不使用浮点小时。
- **并列与分页**：名次由 GreatSQL `RANK()` 在**全体有效成员**的聚合集合上计算；
  分页用 `LIMIT/OFFSET` 下推数据库；「我的排名」复用同一排名子查询后在外层按成员过滤，
  因此与榜单里那一行永远一致且不受分页影响。
- **分类 / 趋势与摘要核对**：集成测试断言
  `Σ categoryDistribution.approvedCount === summary.totalApprovedCount`、
  趋势合计与摘要一致、趋势长度恒为 12 且最后一个月是当前上海自然月。

- **未授权测试**：未登录访问两个接口均返回 **401**；缺少 `analytics:read_internal` 的 actor

- **日志与缓存检查**：两个接口均 `Cache-Control: private, no-store`；
  含 `isCurrentMember` 的响应绝不进入共享缓存；统计读取**不写业务审计日志**（避免放大 `AuditLog`）；

## 基线测试修复（独立于 M5 功能）

### 1. 本地测试运行方式与 `package.json` 不一致（**问题根源**）

排查中发现 `package.json` 的 `test:db` **本来就带 `--test-concurrency=1`**，
而本地包装脚本 `.workbuddy/run.mjs` 漏抄了该参数，导致集成测试以**并行模式**运行。
Node 测试运行器默认按文件并行起进程，而所有集成测试**共用同一个 GreatSQL 库** ——
进程互相插数据，表现为外键冲突、写冲突/死锁、以及 42 项里随机 14~15 项失败。

补上该参数后 **42/42 全绿**（代码未改动）。已修正 `run.mjs` 的 `test:db` / `test:all` 与
`package.json` 对齐。

> 这条不是产品缺陷，而是「本地工具链与项目脚本不一致」——记录在此以免后人重复排查。

### 2. `m0-database.test.ts` 清理序列对残留状态不成立

即便串行执行，该文件的「全表清空 + 重建 fixture」对某些残留状态仍会失败。
已按最小、确定性的方式修复，**未弱化生产外键、未改历史 Migration、未在业务代码规避、
未使用 `FOREIGN_KEY_CHECKS=0`**：

- **`repair_comments.parent_comment_id` 是自引用外键**（回复 → 根评论，`ON DELETE RESTRICT`）：
  一条 `deleteMany()` 会在删根评论时被尚未删掉的回复挡住 →
  改为**两步删**（先删 `parentCommentId != null`，再删 `= null`）。
  `m3-member-dashboard.test.ts` 的 `prepareFixtures` 同样处理。
- **`skills.created_by` → `users`（可空、`ON DELETE RESTRICT`），而 `skills` 是刻意保留的
  共享 seed 数据**：只要任意一行技能带着创建者（测试、预览脚本或历史运行留下），
  全表清空 `users` 就会被外键挡住 → 删 `users` 前先
  `skill.updateMany({ where: { createdBy: { not: null } }, data: { createdBy: null } })`，
  **只解绑引用、不删除共享 seed 技能**（与既有保留 `roles` 的策略一致）。

排查方式（可复用）：查 `information_schema.KEY_COLUMN_USAGE` 枚举全部外键，
标注「引用列是否可空」与「是否在清理集合内」，再对清理集合做拓扑排序 ——
唯一落在集合外的引用表就是 `skills`。
