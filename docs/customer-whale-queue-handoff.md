# 客服小鲸鱼：活动排队人数引导交接（issue #244）

接收方：负责客服小鲸鱼的 bot 管理 agent。Web 需求和改动归属 [#244](https://github.com/ZAFU-PCHospital/zafu-pchospital-web/issues/244)。本说明不代表已部署；先确认对应 Web PR 已合并并上线，再启用新客服文案。本轮 Web 实施者没有修改 bot 配置或发送实际消息。

## Web 提供的能力

- 客户无需登录即可打开本场 `https://pczafu.cn/repair-activities/{activityId}`，查看现场等候人数；优先使用现有活动消息中的完整详情 URL，不凭活动名猜 ID，也不要指向成员/管理接待台。
- 仅统计已签到、尚未接待的客户。未到场报名者、已开始接待者、已删除报名不计入。每 30 秒自动更新，也支持手动刷新；不是秒级推送、个人队号或预计等待分钟数。
- 读取失败会显示不可用/旧值过期提示，不能解读成 0。0 人也不代表能立即接待或现场尚未结束，请遵循活动通知的到场时间。
- 本轮没有预约时间段、限号、停止接待开关、强制签到时段或迟到处罚。不要在客服话术中承诺这些功能。

## bot 管理 agent 要做的配置

只在现有“客服小鲸鱼”的活动通知/报名后到场提醒与相关问答中补一句引导，保留已有通知时机、群范围和去重规则，不新增每 30 秒群内播报或未授权私聊。不修改管理小鲸鱼的人格、活动创建确认流程、凭据或写工具权限。

推荐通知追加文案：

> 出发前可打开本场活动页查看当前等候人数：{activity_url}。人数仅供参考，请按活动通知时间到场。

客户问“现在排多久/什么时候来”时，建议回复：

> 本场活动页可以查看已签到、正在等待接待的人数：{activity_url}。每位客户的处理时间不同，无法按人数准确估算等待时长，请按活动通知时间到场。

不要在固定通知里写死“当前 N 人”，也不要根据 0 人承诺立即接待。没有可核实的本场链接时，说明尚未找到对应活动并请客户提供活动通知，不编造链接。

## 可选的只读接口（本轮配置不要求调用）

如客服未来确需按需查询汇总，可以读取 `GET https://pczafu.cn/api/v1/repair-activities/{activityId}/queue`，无需 Cookie、管理员密码、机器管理 token 或个人身份。

成功信封为 `success:true`，`data` 仅有 `waitingCount` 和 `observedAt`：

- 非负整数：服务端查询时刻的已签到待接待人数。若转述，应明确为该次查询结果，不承诺用户到场时仍相同。
- `null`：签到尚未开放，不能说“无人排队”。
- 404 `ACTIVITY_ENDED` / `ACTIVITY_NOT_FOUND`：沿用既有结束/不存在状态，不继续引用旧数字。
- 超时、非成功信封或其他失败：请客户打开活动页或联系现场工作人员，不填入 0，不猜等待时间。

本轮无需添加 bot 拉取工具：仅链接页面即可完成已确认需求。若新增主动查询行为，仍由 bot 管理 agent 在其项目内确认范围和实现，Web 侧不提供成员/管理接口凭据。

## 配置后的最小核对

由 bot 管理 agent 在受控客服场景验证一条代表性消息：链接确实指向当前活动详情，普通客户可打开，文案不含客户资料、不保证等待时长，原有通知没有重复发送。Web 未部署时不对外宣称已上线；无需批量发通知、查询生产客户名单或创建测试报名。
