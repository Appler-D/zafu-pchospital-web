# 统一账号门禁：分阶段启用与回退（Refs #146 / Refs #113）

本文件是**上线操作说明**，不是实现说明。契约语义见 [API 契约](contracts/api-v1.md)，
判定与依赖方向见 [架构](architecture.md) 第 3.6 节，邮箱操作口径见 [邮箱管理](email-management.md)。

本轮交付只包含「可启用的代码 + 本说明」：**不修改生产配置、不部署、不实际开启全员门禁**。
改动无 Migration、无新依赖（Nodemailer 已在依赖里），因此启用与回退都只涉及
`EMAIL_GATE_MODE` 一个变量与进程重启。

## 1. 档位事实（先读这一节再动手）

| 档位    | 受约束的账号                                              | 不受约束               |
| ------- | --------------------------------------------------------- | ---------------------- |
| `off`   | 无（缺省值；保持既有「邮箱非强制」行为，不读邮箱表）      | 全部已认证账号         |
| `admin` | **当次**持有 ADMIN 角色的账号（双角色访问成员侧同样受限） | 只有 MEMBER 角色的账号 |
| `all`   | 全部已认证账号                                            | 无                     |

- 判定顺序固定：有效 Session / 账号资格 → 必须改密 → 当前档位需要已验证邮箱且无有效豁免 →
  原目标或角色默认页。**改密永远优先**，豁免只豁免邮箱这一步。
- 豁免最长 7 天（1–168 小时）、必须带原因与操作人；豁免不授予权限、不授予找回资格、
  不绕过改密。
- 邮件通道与门禁**解耦**：`MAIL_ENABLED` 关闭、SMTP 故障、预算耗尽都不会让门禁自动失效，
  也不会让门禁额外拦住原本可访问的功能。遇到发信故障用「按账号、短时、留痕」的豁免处理。
- `EMAIL_GATE_MODE` 只从服务端环境读取：没有 `NEXT_PUBLIC_*`、没有请求参数、没有前端存储
  可以改变它；非法值直接 500 `EMAIL_GATE_MODE_INVALID`，**不会静默按 `off` 运行**。
- 历史数据口径：`verifiedAt` 有值但 `active_email_key` 为空的有效邮箱身份仍算已验证，
  不需要为此回填；同一账号存在多条邮箱身份时不猜选，按「未验证」处理（需人工核对）。

## 2. 启用顺序（每一步都有判据，不满足就停在原地）

发布统一走仓库脚本 `tools/deploy/deploy-prod.sh`（本地构建 + 上传产物），按现有部署流程
约定停机窗口。改档位需要重启全部实例（脚本或 `systemctl restart` 应用服务），改的是
生产 `.env` 里的一行。

### 第 0 步：以 `off` 档发布代码

1. 生产 `.env` 写入 `EMAIL_GATE_MODE=off`（缺省值，写明确比不写更好排障）。
2. 发布 → 冒烟：站点公开页与站内文档全部 200；`GET /api/v1/me` 返回 200 且带
   `accountAccess`；任一未绑定邮箱的既有账号仍能正常调用业务 API（`off` 档不读邮箱表）。
3. 判据：这一轮**行为与上一版完全一致**。出现任何 403 `EMAIL_VERIFICATION_REQUIRED`
   即为配置或代码问题，先回退再排查。

### 第 1 步：真实应用收码联调（需要外部条件，未完成不得进入下一步）

自动测试覆盖到 Fake Sender 为止，**真实「应用发码 → 用户收码 → 页面确认」仍未验证**。
需要先具备两个由使用者提供的条件：一个受控测试账号、一个可收信的测试邮箱地址。

> **没有「管理员替账号预绑定已验证邮箱」这种能力**，也不许造这种能力：目标邮箱必须经过
> 验证码证明确实收得到。「账号邮箱」面板（任务 4）能做的是核对脱敏绑定状态、 revealing、
> 创建**协助待办**与授予豁免，其中协助只跳过「旧邮箱取证」这一步，**不跳过目标邮箱验证**。

1. 由**受控账号本人**登录 `/account/email` → 填目标邮箱 → 发码 → 收码 → 确认。
   这是该账号拿到「已验证邮箱」的**唯一**路径。
2. 若该账号旧邮箱已不可用（换绑受阻）：由持有 `member:manage` 的**另一位**管理员在
   「账号邮箱」面板创建协助待办，本人带 `currentPassword` 与目标邮箱的验证码完成确认 ——
   协助跳过的是旧邮箱取证，目标邮箱照旧必须收码验证。
3. 核对确认后的 `destination` 是否回到原目标、Cookie 是否轮换、会话是否按预期继续有效。
4. 若收不到信：先按 [邮箱管理](email-management.md) 的排查口径处理，给该账号一条短时豁免
   继续验证其它环节，并记录豁免原因与操作人。
5. 判据：至少一条真实收码闭环通过，才认为「开启门禁后用户能自己解锁」。

> 这一步没有完成时，后面的档位一律不要开。缺条件就在交付记录里写「上线前待联调」，
> 不要把 Fake Sender 或传输层成功当作生产收码。

### 第 2 步：切档前的准备（改 `EMAIL_GATE_MODE` **之前**完成）

管理员可用性、必要豁免这些准备工作属于**切换的前置条件**，不是切到 `admin` / `all`
之后再补的「提前动作」—— 门禁一旦生效，没邮箱的管理员连恢复入口外的接口都打不开，
现场补救只会把小事变成锁死。

1. 逐个点名当前的 ADMIN 名单：每一位都必须**已经**有已验证邮箱，或由另一位管理员授予
   有效豁免（不能自己给自己授）。判据：假定档位已经是 `admin`，这一位还能进 `/account/email`
   并把流程走完。
2. 对确实处在换邮箱 / 收信失败中的账号按人授予 1–7 天豁免并留痕（原因 + 操作人）。
3. 复核窄例外恢复入口仍在：`/account/email` 上常驻的「账号恢复」「账号邮箱」
   （`account-recovery` 用途，只豁免邮箱这一道，权限与审计照旧）。
4. **每一次改档位之前都重新走一遍本节**（管理员名单会变）；准备没做完就停在 `off`。
5. 判据：不存在「切档后需要靠数据库手工改角色 / 伪造验证状态才能进后台」的账号。

### 第 3 步：`admin` 档

1. 生产 `.env` 改为 `EMAIL_GATE_MODE=admin` → 重启全部实例。
2. 冒烟（代表**已有 Session**，不重新登录）：
   - 未验证邮箱的管理员：后台页面重定向到 `/account/email`；业务 API 返回
     403 `EMAIL_VERIFICATION_REQUIRED`（不是 401，前端不当作过期）；
     `GET /api/v1/me` 仍是 200 且 `accountAccess.state = EMAIL_VERIFICATION_REQUIRED`；
     登出仍可用；`/api/v1/admin/accounts/lookup`、`/api/v1/admin/accounts/:userId/password-reset`
     与任务 4 的 `/api/v1/admin/accounts/:userId/email*` 恢复端点仍可达。
   - 已验证邮箱的管理员：后台与成员侧全部正常。
   - 只有 MEMBER 角色的账号：不受本档影响（同第 0 步结果）。
3. 判据：管理员侧「能被拦住也能自助解锁」，成员侧无任何变化。

### 第 4 步：`all` 档

1. 生产 `.env` 改为 `EMAIL_GATE_MODE=all` → 重启全部实例。
2. 前置：第 2 步那份准备必须**已经按 `all` 的范围重做一遍**（此时不只管理员，全部已认证账号
   都被约束）。已知必用账号要逐条对上「已验证邮箱」或「有效豁免」，不接受任何
   「先开了再说」或自动放行的做法。
3. 冒烟：代表性成员页（工作台、维修列表 / 详情、活动报名、通知、个人主页）与代表性
   成员 / 管理业务 API 各一组，加管理员侧同类项。未验证邮箱的账号统一被引导到
   `/account/email`，完成后回到原目标。
4. 判据：无「登录后无处可去」的账号；`/account/email` 上的「继续原目标」只在服务端确认
   已验证或有有效豁免后可点。

## 3. 回退

- **档位回退（首选，秒级生效于下一次请求）**：把 `EMAIL_GATE_MODE` 改回上一档 →
  重启全部实例。已完成邮箱验证、有效豁免与所有邮箱相关数据**全部保留**，
  不做任何数据回滚，也不删身份行。
- **版本回退**：`bash tools/deploy/deploy-prod.sh --rollback` 换回上一版产物。
  本功能无 Migration，产物回退即可，不需要还原数据库。
- **个别账号被锁**：用管理员恢复入口（`/account/email` 上常驻的「账号恢复 / 账号邮箱」，
  或后台成员页同一组件）核对状态并按需授予豁免；这是正常运维动作，不是回退。
- **大范围锁死**：按上面的顺序档位回退到 `admin` 或 `off`，并在运维记录里写清
  时间、操作人、档位、原因与影响范围；恢复后再逐个排查。
- **没有任何可认证的管理员**：这属于账号 / 运维恢复问题，**不能靠关门禁解决** ——
  档位与 `off` 不会恢复被禁用、被撤销身份或不存在凭据的账号，也不要把「关门禁」
  当作找回手段。

## 4. 禁止事项（评审时逐条对照）

- 不为验证门禁去开 `SELF`（自己给自己建协助 / 授豁免 / 续豁免一律服务端拒绝）。
- 不伪造 `verifiedAt`、角色、成员资格或找回资格来「让流程走通」。
- **不由管理员预绑定、直写数据库或任何别的手段制造「已验证邮箱」**：目标邮箱必须经过它自己的
  验证码确认。管理员侧的协助待办只跳过旧邮箱取证，邮箱门禁的解锁永远走本人收码那一条路。
- 不新增无鉴权的重置端点，不放宽 `assertSameOrigin`、权限码与审计入口。
- 不给 `/admin/*` 或 `/admin/accounts/*` 加前缀式放行；豁免端点清单就是那一小节列出的几条。
- 不延长 `rememberMe`、Session 或临时密码的既有时限，不改变 #113 的受限短时 Session。
- 不因发信失败自动关闭门禁，也不把门禁拒绝写成会话过期。
